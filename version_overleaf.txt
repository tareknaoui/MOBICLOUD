\chapter{Chapter 5: Implementation}

\section{Introduction}
The exponential growth of data generated by mobile devices has made decentralised storage one of the central challenges of modern Big Data engineering. Rather than relying on a centralised cloud infrastructure, MobiCloud proposes to transform a set of ordinary smartphones into a cooperative distributed storage cluster, applying at mobile scale the same fault-tolerance principles that underpin large-scale Big Data systems such as HDFS, Ceph, and Azure Data Lake Storage.

Having completed the design of our system, we present in this final chapter the implementation and deployment of the MobiCloud mobile application. First, we enumerate and describe all the software tools that enabled us to bring our work to fruition. We then outline the security mechanisms put in place to guarantee data confidentiality. Next, we present the hardware environment used for testing along with the results obtained. Finally, a concrete view of the application is illustrated through screenshots representing its most important interfaces.

\section{Development Environment}
The implementation of a distributed storage system at mobile scale requires a technology stack that combines reliability, performance, and native support for concurrent and networked operations, qualities that are equally central in traditional Big Data engineering. The tools and frameworks selected for MobiCloud are presented below.

\subsection{Android Studio}
\begin{center}
\IfFileExists{Figs/logos/android-studio.png}{\includegraphics[height=1.2cm]{Figs/logos/android-studio-icon.png}}{}
\end{center}

Android Studio is the official Integrated Development Environment (IDE) for the Android platform. Developed by Google and built on IntelliJ IDEA, it provides a complete set of tools for designing, developing, testing, and deploying Android applications.

Android Studio incorporates an advanced Android emulator, a visual layout editor, performance profiling tools, and native support for the Gradle build system. It supports both Kotlin and Java, and offers intelligent code completion along with an integrated debugger.

We chose Android Studio because of its native integration with the Android SDK, its first-class Kotlin support, and the comprehensive toolchain it provides for building, testing, and deploying the MobiCloud application.

\subsection{Kotlin}
\begin{center}
\IfFileExists{Figs/logos/kotlin.png}{\includegraphics[height=1.2cm]{Figs/logos/kotlin.png}}{}
\end{center}

Kotlin is a modern, statically typed programming language developed by JetBrains. It became the officially recommended language for Android development by Google in 2019. Kotlin is fully interoperable with Java and runs on the Java Virtual Machine (JVM).

Kotlin offers a concise and expressive syntax that significantly reduces the amount of boilerplate code compared to Java. It natively supports nullability handling, coroutines for asynchronous programming, extension functions, and data classes. These features produce code that is safer, more readable, and more maintainable.

We chose Kotlin for its native coroutines support, which allowed us to manage network and storage operations in an asynchronous, non-blocking manner --- an essential requirement in a distributed storage system where multiple data streams must be handled concurrently without blocking the main thread.

\subsection{Jetpack Compose}
\begin{center}
\IfFileExists{Figs/logos/compose.png}{\includegraphics[height=1.2cm]{Figs/logos/Jetpack_Compose_logo.png}}{}
\end{center}

Jetpack Compose is Google's modern UI toolkit for building native Android interfaces. It adopts a declarative paradigm that simplifies and accelerates UI development by allowing the interface to be described as a function of the application state.

Unlike the traditional XML-based approach, Jetpack Compose allows the entire user interface to be defined directly in Kotlin. The UI automatically updates whenever the application state changes, a process known as recomposition. Compose integrates natively with other Jetpack components such as ViewModel, Navigation, and LiveData.

Choosing Jetpack Compose allowed us to build reactive, modern interfaces following Material Design 3 guidelines, while maintaining a unified and consistent code base across all screens of the MobiCloud application.

\subsection{Hilt}
\begin{center}
\IfFileExists{Figs/logos/hilt.png}{\includegraphics[height=1.2cm]{Figs/logos/hilt.png}}{}
\end{center}

Hilt is a dependency injection framework for Android developed by Google, built on top of Dagger. It simplifies dependency injection in Android applications by providing standardised containers for each Android component.

Dependency injection is a design pattern that decouples the components of an application by supplying their dependencies from outside rather than having them instantiate those dependencies themselves. Hilt automates this management by generating the required wiring code at compile time, eliminating runtime errors and improving the testability of the application.

We used Hilt to manage dependencies between the various layers of the MobiCloud architecture --- in particular between use cases, repositories, and network services --- in accordance with the Clean Architecture adopted in this project.

\subsection{Room}
\begin{center}
\IfFileExists{Figs/logos/room.png}{\includegraphics[height=1.2cm]{Figs/logos/room.png}}{}
\end{center}

Room is a data persistence library developed by Google as part of the Jetpack suite. It provides an abstraction layer over SQLite, enabling access to the local database in a more fluid manner while retaining the full power of SQLite.

Room consists of three main components: entities, which represent database tables; DAOs (Data Access Objects), which define the data access methods; and the Database class, which serves as the main access point to the persistent database. Room validates SQL queries at compile time, preventing runtime errors.

We chose Room to locally persist the distributed file catalogue, fragment metadata, and cluster member information. This local persistence layer plays a role analogous to that of a local data node cache in a Hadoop cluster: it guarantees data availability and query speed even when network connectivity is lost.

\subsection{Ktor}
\begin{center}
\IfFileExists{Figs/logos/ktor.png}{\includegraphics[height=1.2cm]{Figs/logos/ktor.png}}{}
\end{center}

Ktor is an asynchronous framework for building server and client applications in Kotlin, developed by JetBrains. It is built on Kotlin coroutines and provides a clean, intuitive API for constructing web services and WebSocket servers.

Ktor follows a modular architecture in which each feature is provided as a plugin. It natively supports WebSockets, HTTP routing, JSON serialisation, and TLS connections. Its lightweight footprint and high performance make it well suited for embedded servers and microservices.

In MobiCloud, Ktor was used to develop the WebSocket relay server responsible for signalling and message transport between peers located behind separate NATs. This server fulfils a role comparable to that of a coordinator node in a distributed system: it routes control messages between clusters and enables devices on 4G and Wi-Fi networks to communicate transparently. The relay server was deployed on Render (Frankfurt, Germany), ensuring low-latency connectivity for our test devices.

\subsection{Android NDK and C++}
\begin{center}
\IfFileExists{Figs/logos/android-ndk.png}{\includegraphics[height=1.2cm]{Figs/logos/android-ndk.png}}{}
\quad
\IfFileExists{Figs/logos/cpp.png}{\includegraphics[height=1.2cm]{Figs/logos/cpp.png}}{}
\end{center}

The Android NDK (Native Development Kit) is a set of tools that allows native code written in C or C++ to be embedded in an Android application. It is particularly suited to processing tasks that require high performance, such as signal processing, low-level cryptography, and coding algorithms.

The NDK uses the Java Native Interface (JNI) as a bridge between Kotlin/Java code and native C++ code. Native libraries are compiled via CMake into \texttt{.so} files that are loaded dynamically at application startup. This approach grants access to low-level system resources while benefiting from the execution speed of native code.

We used the NDK to implement the Reed--Solomon erasure coding algorithm directly in C++. Erasure coding is one of the fundamental data redundancy techniques in Big Data storage systems --- it is notably used by Google Colossus, Facebook f4, and Apache HDFS Erasure Coding --- because it provides strong fault tolerance at a much lower storage overhead than simple replication. Our implementation uses a $(K=4,\,N=2)$ configuration: each file is divided into 4 data fragments and 2 parity fragments, for a total of 6 fragments. The original file can be reconstructed from any 4 of the 6 fragments, tolerating the simultaneous loss of any 2 nodes. Implementing this algorithm in native C++ rather than Kotlin was necessary to meet the real-time performance requirements of fragmentation and reconstruction on resource-constrained mobile hardware.

\subsection{React}
\begin{center}
\IfFileExists{Figs/logos/react.png}{\includegraphics[height=1.2cm]{Figs/logos/react.png}}{}
\end{center}

React is an open-source JavaScript library developed by Meta for building interactive user interfaces. It is based on a component-driven architecture in which each element of the interface is an autonomous, reusable unit.

In MobiCloud, React was used to develop the relay server administration dashboard. This web interface provides a real-time view of the relay server's activity (active WebSocket connections, connected peers, traffic metrics, and server health indicators) and served as our primary observability tool throughout all test sessions.

\section{Security}
Security and data confidentiality are critical concerns in any distributed storage system --- all the more so in a fully decentralised architecture where, unlike a conventional cloud data centre, there is no single trusted operator controlling the storage nodes. In MobiCloud, user data transits through and is stored on devices owned by third parties, which imposes strict security mechanisms at every level of the system. This constraint is structurally similar to the one faced by Big Data systems that store sensitive data across heterogeneous commodity nodes in multi-tenant environments.

We focused on three fundamental aspects of security: node identity, fragment encryption, and secure key distribution.

\subsection{Node Identity}
To ensure the authenticity of each participant in the MobiCloud network and prevent any identity spoofing, every device holds a unique cryptographic identity generated and protected by the Android Keystore system.

The Android Keystore is a secure storage system for cryptographic keys. On devices equipped with a hardware security module (TEE, Trusted Execution Environment), private keys never leave the hardware and cannot be extracted even by an application with elevated privileges. This hardware-backed protection ensures that a node's identity is irrevocably bound to the physical device that hosts it.

\subsubsection{Identity Generation}
At first launch, MobiCloud generates an asymmetric EC (Elliptic Curve) key pair on the secp256r1 (P-256) curve directly inside the Keystore. The public key constitutes the node's permanent identifier in the network. Every message sent by a peer is digitally signed with its private key, allowing other nodes to verify its authenticity before any processing takes place.

\subsubsection{Peer Verification}
Upon receiving a message, the destination node verifies the sender's digital signature against its known public key. Any message with an invalid signature is immediately discarded. This mechanism prevents the injection of forged messages into the network and guarantees the integrity of all communications between peers.

\subsection{Fragment Encryption}
To ensure the confidentiality of data stored at peer devices, every file fragment is individually encrypted before being transmitted or stored on a third-party device. The algorithm used is AES (Advanced Encryption Standard) in GCM (Galois/Counter Mode) with 256-bit keys.

AES is the most widely adopted symmetric encryption standard. GCM mode combines stream encryption with data authentication, guaranteeing both the confidentiality and the integrity of each fragment. Each encryption operation uses a unique randomly generated 96-bit Initialisation Vector (IV), making it impossible to infer any information by comparing ciphertexts.

Among the advantages of the AES-GCM algorithm, we highlight:
\begin{itemize}
\item A high security level (256 bits) recognised by NIST as the US federal encryption standard;
\item Integrated data authentication via the GCM tag, which detects any alteration of the fragment before decryption;
\item Excellent execution performance thanks to hardware AES acceleration present in modern ARM processors.
\end{itemize}

\subsection{Key Distribution}
Secure distribution of encryption keys between peers is a fundamental challenge in decentralised systems. MobiCloud uses a key exchange protocol based on ECDH (Elliptic Curve Diffie--Hellman) combined with HKDF (HMAC-based Key Derivation Function) to establish shared keys without any secret ever being transmitted in plain text over the network.

ECDH allows two parties to derive a shared secret from their respective public keys without any prior communication of a secret value. This shared secret is then passed to HKDF, which produces a derived AES-256 key that is unique to the communicating pair of devices.

This approach guarantees Perfect Forward Secrecy: even if a private key is compromised at a later date, past sessions remain protected.

\section{Testing}
In order to validate the implementation of our work, we tested it in an environment representative of real-world usage conditions. A minimum of six storage nodes is required to distribute the six fragments produced by the $(K=4,\,N=2)$ Reed--Solomon scheme --- one fragment per node. Our cluster was composed of one cluster head coordinator and six regular member devices, for a total of seven smartphones.

\subsection{Test Results}
We tested file distribution and retrieval for files of varying sizes across the seven-device cluster (one cluster head + six regular members). Each test distributes a file as 4 data fragments and 2 parity fragments across the 6 regular member nodes, one fragment per node. Since all communication in MobiCloud is routed through the single Render relay server hosted in Frankfurt, the relay latency is a constant factor regardless of whether the communicating peers belong to the same cluster or different clusters. The variable that determines transfer time is therefore exclusively the upload bandwidth of the sending device's network connection. The results are presented in Table~\ref{tab:test-results}.

\begin{table}[H]
\centering
\begin{tabular}{|l|l|l|l|l|}
\hline
 & \textbf{File size} & \textbf{Network condition} & \textbf{Distribution time} & \textbf{Retrieval time} \\
\hline
File 1 & 1 MB & Wi-Fi 802.11ac (all nodes) & 1.4 s & 1.1 s \\
\hline
File 2 & 10 MB & Wi-Fi 802.11ac (all nodes) & 5.3 s & 4.0 s \\
\hline
File 3 & 50 MB & 4G LTE, Djezzy (source node) & 42 s & 47 s \\
\hline
\end{tabular}
\caption{Summary of test results.}
\label{tab:test-results}
\end{table}

The results show consistent and predictable performance. For Files 1 and 2, all nodes were connected via Wi-Fi, providing sufficient upload bandwidth to the Frankfurt relay. For File 3, the source device was connected via 4G LTE (Djezzy), whose uplink speed averaged 5~Mbps during the test; this bandwidth constraint alone explains the higher transfer time, since the relay server itself introduced no additional bottleneck. This behaviour is consistent with the I/O-bound patterns observed in Big Data pipelines that rely on wide-area network links, where the bottleneck is always the last-mile upload capacity rather than the processing or routing infrastructure.

We also tested cluster resilience against cluster head failure. After forcibly stopping the coordinator node (Oppo Reno 12), a new cluster head was elected by the Bully algorithm in an average time of 97 seconds, which is consistent with the configured parameters (a 90-second timeout followed by the exchange of election messages). During the entire failover period, all 6 fragments remained accessible on the member nodes and file retrieval continued uninterrupted, confirming the fault-tolerance guarantee of the $(K=4,\,N=2)$ erasure coding scheme.

\section{Conclusion}
Throughout this chapter, we have presented the various development tools that enabled us to deliver the MobiCloud application. The chosen technologies --- Kotlin, Jetpack Compose, Hilt, Room, Ktor, the Android NDK, and React --- form a coherent and modern stack well suited to the demands of a distributed storage system operating at mobile scale.

The security mechanisms put in place, namely cryptographic identity via Android Keystore, AES-256-GCM fragment-level encryption, and key distribution via ECDH-HKDF, ensure the confidentiality and integrity of user data even when it is stored on third-party devices.

The tests carried out on a real cluster of seven smartphones validated the core features of the system: automatic peer discovery, fault-tolerant file distribution using $(K=4,\,N=2)$ Reed--Solomon erasure coding, and cluster resilience in the face of cluster head failure. From a Big Data engineering perspective, MobiCloud demonstrates that distributed storage principles (horizontal scalability across commodity nodes, erasure-coded redundancy, and decentralised coordination) can be applied effectively on heterogeneous mobile hardware.
